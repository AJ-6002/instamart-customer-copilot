# Instamart Customer Intelligence \& Support Copilot

## Overview

A four-part capstone that turns messy, synthetic Instamart-style exports into a customer-intelligence and support tool. All data is synthetic and fictional, generated by `generate\_data.py`; all money is in Indian Rupees (INR). No API key, account or network call is used: every language-model call goes through the offline `mock\_llm.py`.

|Part|What it does|
|-|-|
|A|Audits and cleans the raw exports, stores them in SQLite, answers business questions in SQL and pandas|
|B|Segments customers (RFM + K-means) and predicts who will lapse|
|C|Triage of support tickets with privacy, retry, validation and budget guardrails|
|D|Policy RAG assistant and a tool-using refund agent|

`generate\_data.py` and `mock\_llm.py` are the two supplied files and are committed unmodified. Everything else is my own work.

## Reproduce

Run from the repository root (Python 3.11+).

1. `python -m venv venv`
2. `venv\\Scripts\\activate` (Windows) or `source venv/bin/activate` (macOS/Linux)
3. `pip install -r requirements.txt`
4. `python generate\_data.py` (last line: `generated: customers=1200 products=40 orders\_raw=13084 tickets=164`)
5. `python part\_a\_audit.py`
6. `python part\_a\_clean.py` (writes `data/clean/\*.csv` and `data/instamart.db`)
7. `python validate\_part\_a.py` (last line: `ALL CHECKPOINTS PASSED`)
8. `python run\_queries.py`
9. `python part\_a\_analysis.py`

Steps for Parts B to D will be added here as those scripts are written.

### Cleaning rules and what each changed

**Customers**

|Rule|Effect|
|-|-|
|City: strip spaces, title case|24 spellings become 6 cities|
|Gender: map to male / female / unknown (blank becomes unknown)|10 spellings plus 30 blanks become 3 values|
|Age: values outside 10-100 set to missing, then fill with the city median (groupby + transform)|6 values set to missing; 0 missing afterwards, all ages between 18 and 60|
|signup\_date converted to datetime|all 1,200 rows|

Result: Pune 227, Delhi 210, Bengaluru 197, Chennai 191, Hyderabad 191, Mumbai 184; female 610, male 560, unknown 30.

**Orders** (applied in this order)

|#|Rule|Effect|
|-|-|-|
|1|Convert order\_ts to datetime|no rows change|
|2|Remove exact duplicate rows|119 rows removed|
|3|Per order\_id keep the record with the latest order\_ts (drops earlier pending records)|656 rows removed|
|4|order\_amount to numeric; fill missing from `round(price\_inr x quantity x (1 - discount\_pct/100), 2)`|112 values filled|
|5|Negative delivery\_minutes set to missing; for completed orders fill with the median of the product category among completed orders; cancelled orders stay missing|105 negative values set to missing; 0 missing among completed, 1,199 missing among cancelled (by design)|

Rules 4 and 5 report counts after rules 2 and 3, so they are slightly below the raw audit counts (120 and 106): some of the bad rows were duplicates or pending records that rule 2 and rule 3 already removed.

**The four questions (max 200 words, write this in your own words):**

**The data shows simulated Instamart orders of groceries, dairy, snacks, personal care items and electronics from six cities in India. We have a total of 11,110 completed orders. The order amount has a heavily right-skewed distribution, with a mean of INR 269.91 and a median of only INR 135.00. The skewness is about 4.61, meaning a small number of large values pull the average up. Using the 1.5 x IQR rule (fences at -283.50 and 645.30), 897 orders are above the upper fence and none are below, so these are outliers. The strongest relationship is between order\_amount and discount\_pct (-0.095), followed by order\_amount and quantity (+0.087). However, these correlations are very weak and do not establish causation.**
